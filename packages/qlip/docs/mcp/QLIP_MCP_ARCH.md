# QLIP MCP Architecture

Understood. The correct mental model for MCP is: QLIP becomes a server that exposes "Tools" (callable functions) plus optional Resources (read-only data) and Prompts (guided workflows) that an LLM client can discover and invoke. That matches the MCP spec's tool/resource/prompt concepts. (Model Context Protocol)The key design constraint you're implying is important:You do not want an LLM to "send Python classes" at runtime (that's unsafe and non-portable).You want an interface where the LLM selects registered constraints/guidance modules by name + parameters, and QLIP composes them deterministically.That is exactly how you make QLIP a reusable framework and a safe MCP server.

1) Architecture: QLIP as a framework + QLIP as an MCP server

Layer A - QLIP Framework (pure Python library)Core responsibilities:Parse problem input (chemistry, template/grid, candidate sites)Build a MILP model (Pyomo) with:hard constraints (feasibility)objective (base objective, e.g., energy)optional soft guidance (penalties, lexicographic objectives, epsilon-constraints)Solve with Gurobi onlyDecode solution to structure artifacts + certificates/witnesses

Layer B - QLIP MCP Server (thin wrapper)Responsibilities:Expose QLIP's capabilities as MCP tools:qlip.solveqlip.list_constraintsqlip.list_guidanceqlip.validate_requestqlip.explain_infeasibility (if you can extract IIS / conflict refiner info)Provide MCP resources for discoverability:constraint catalogguidance catalogschema versionsProvide MCP prompts to teach the LLM "how to use QLIP safely" (multi-step solve + refine loop). (Model Context Protocol)Transport: for early work, use stdio MCP (local), because it's simpler and avoids exposing a solver service on a network. Security issues with exposed MCP servers are increasingly common; do not run unauthenticated remote MCP unless you have an auth story. (Bitsight)

2) The interface you want: "pass constraints/guidance classes" safelyDo not accept arbitrary codeLetting an LLM send Python code or class definitions is a direct path to RCE and prompt-injection chains (this has already been a real-world issue in MCP tooling). (TechRadar)Do accept "registered modules + parameters"Define two plugin interfaces:Constraint interface (hard feasibility)name / idJSON schema for parametersapply(model, allocation, params) -> Nonemetadata: what it needs (sites, distances, motif artifacts), whether it introduces binaries, etc.Guidance interface (soft / preference)name / idJSON schema for parametersapply(model, allocation, params) -> GuidanceContributione.g., add weighted penalty terms, lexicographic levels, or epsilon constraintsThen you implement a registry:ConstraintRegistry: id -> ConstraintClassGuidanceRegistry: id -> GuidanceClassThe MCP tool request never contains code; it contains:{ "chem": "SrTiO3", "grid": 2, "constraints": [ {"id": "proximity.atomic_radii", "params": {"scale": 1.0}}, {"id": "motif.linking", "params": {"motif_dir": "...", "include": ["octahedra"]}} ], "guidance": [ {"id": "objective.energy_spp", "params": {"weight": 1.0}} ], "solver": {"name": "gurobi", "time_limit_s": 60}}This is composable, deterministic, and safe.

3) MCP surface: tools, resources, promptsTools (MCP "tools" capability) (Model Context Protocol)Minimum set I recommend:qlip.list_constraintsreturns: [ {id, title, description, params_schema, tags} ]qlip.list_guidancereturns: [ {id, title, description, params_schema, tags} ]qlip.validate_requestvalidates a solve request against schemas and local environment requirements (Gurobi, POT root, motif artifacts if requested)qlip.solveruns the full build/solve/decodereturns:status: OPTIMAL | FEASIBLE | INFEASIBLE | ERRORobjective_valueartifacts: CIF as text, plus any lightweight metadatacertificates: bounds/certificates, or IIS summary if infeasiblerun_log: solver summary, timing, selected constraints, etc.qlip.explain_failuretakes a prior run_id (or embedded solver log)returns a structured explanation:missing assets (POT pairs)constraint conflicts (IIS if available)suggestion: "remove constraint X or loosen param Y"Resources (MCP "resources") (Model Context Protocol)Good candidates:qlip://catalog/constraintsqlip://catalog/guidanceqlip://schemas/solve_request/v1qlip://examples/stoic/SrTiO3These help clients browse capabilities without invoking tools.Prompts (MCP "prompts") (Model Context Protocol)Add at least one structured workflow prompt:prompt.solve_refineStep 1: validate requestStep 2: solveStep 3: if infeasible, call explain_failureStep 4: propose minimal edit set (remove/relax constraints)Step 5: re-solveThis is how you turn QLIP into an LLM-friendly "co-scientist loop" without custom agent glue everywhere.

4) The "framework" part: how others reuse QLIP beyond MCPTo make QLIP a framework:Keep the solver core importable as qlip.coreKeep plugins importable as qlip.plugins.constraints.* and qlip.plugins.guidance.*Provide a stable SolveRequest (Pydantic/dataclass) + schema exportProvide a single solve(request: SolveRequest) -> SolveResultThen:MCP server calls qlip.solve(request)Other apps (scripts, pipelines, notebooks) call the same functionThat avoids duplication and guarantees that "MCP usage" doesn't diverge from "library usage".

5) Security and operational guardrails (important for MCP)Because MCP servers are increasingly being deployed insecurely (many exposed without auth) and tool-chaining vulnerabilities have been reported, treat QLIP MCP as local-only by default. (Bitsight)Hard guardrails:No arbitrary file paths unless explicitly whitelisted (motif_dir, pot_dir)Do not allow tools that execute shell commandsRate-limit solve calls and enforce:time limitsvariable limitsmemory caps where possibleReturn artifacts as text blobs (CIF) rather than writing to arbitrary disk paths unless you implement a safe output directory.

6) Concrete build plan (next implementation steps)Stabilize core APIDefine SolveRequest + SolveResultImplement plugin registries + JSON schemas per pluginRefactor current CLI to call the core APICLI becomes a thin adapter (proves your framework boundary is correct)Implement MCP server wrapperExpose list_constraints, list_guidance, validate_request, solveAdd prompts for the refine loopAdd "certificate" plumbingIf infeasible: attempt IIS/conflict extraction via Gurobi/Pyomo hooks (where possible)Return structured witnessesAdd a small "capabilities resource"So clients can discover tool schemas without guessingIf you want to move immediately, the next thing I would draft is the exact JSON schema for SolveRequest and the plugin parameter schemas (because that locks the interface and makes MCP tools trivial to expose).
