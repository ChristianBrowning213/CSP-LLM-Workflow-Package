# Crystal-DB Property Audit

## 1. Executive summary

Crystal-DB currently has one persisted scientific target-like property on database structures: `band_gap_eV`. It is present in the SQLite schema, surfaced in descriptors, fingerprints, CrystalCards, the legacy `query_structures` CLI/API, and candidate report comparators. It is range-filterable and sortable through `crystal_db.query.query_structures`.

The default MCP database configured by `mcp_server/server.py` (`data/phase6_mp_10k.db`) has 10,000 structures from Materials Project CIF ingestion, but `band_gap_eV` coverage is 0/10,000. In that corpus, no stored scientific property is dense enough for looping runs such as "search this composition/material family and optimise for high band gap".

MCP retrieval tools (`crystal.text_search`, `crystal.csp_pack`, `crystal.novelty_check`) do not expose a property-filter or property-sort input. They perform text and/or fingerprint retrieval. A user can put words like "high band gap" into the free-text query, but the system treats that as semantic text retrieval, not as a validated numeric property constraint. `crystal.csp_pack` returns neighbor metadata/provenance and hints, but it does not currently return explicit property metadata such as `band_gap_eV`. `crystal.novelty_check` returns comparator IDs and similarity scores only.

Candidate-side metadata may include `predicted_energy`, `energy`, `band_gap_eV`, `predicted_band_gap_eV`, or `target_band_gap_eV`, but these live in CSP candidate manifests/reports, not as queryable per-structure database properties. `predicted_energy` is not a stored database property for retrieved structures.

## 3. Current MCP exposure

The MCP server exposes these tools: `crystal.text_search`, `crystal.agent`, `crystal.novelty_check`, `crystal.csp_pack`, `crystal.status`, and `crystal.bench_retrieval`.

Current answers:

1. A user cannot query by numeric property through the MCP tool schemas. There is no `property_filter`, `band_gap_eV_min`, `order_by`, or objective input on MCP tools.
2. A user can type "high band gap" or "low formation energy" into `query`, but the system treats it as semantic text. It does not validate that the property exists, filter numerically, or sort by property. Formation energy is not present as a stored structure property.
3. `csp_pack` does not expose explicit property metadata in neighbor results. It returns neighbor IDs, retrieval scores, provenance, redaction state, text docs, hints, and export metadata. Hints use formula and space group internally, but `band_gap_eV`, `volume`, and `nsites` are not emitted as a property block.
4. `novelty_check` exposes no property information. Comparators contain `structure_id`, `score`, and `mode`; novelty contains similarity thresholds and max similarities.
5. Properties are not passed through to Skill-Loop-CSP currently. The repository has no Skill-Loop-CSP integration surface; the MCP/CSP pack payload has no explicit property objective or property metadata channel.

## 4. Best candidate loop objectives

There are no currently dense scientific target properties in the main MCP corpus. The best candidates are therefore split into "future objective" and "current loop constraints":

| rank | property/axis | status | recommendation |
|---|---|---|---|
| 1 | `band_gap_eV` | Implemented and queryable outside MCP, but 0/10,000 coverage in main MCP DB | Best future scalar objective after population, units, provenance, and MCP filtering/sorting are added. |
| 2 | `volume` | Dense numeric descriptor, 10,000/10,000 in main MCP DB | Usable now as a structural constraint or ranking axis, not as a scientific optimisation objective. |
| 3 | `formula` / `elements_csv` | Dense metadata | Usable now for composition/material-family loop constraints. |
| 4 | `space_group` | Metadata/facet | Usable as a structural-family constraint if coverage is verified for the target DB. |
| 5 | semantic text/fingerprint similarity | Dense retrieval representation | Usable to retrieve analogous structures, but not a property objective. |

## 5. Properties not suitable for optimisation

- `fingerprint_vector`: a mixed retrieval vector, not a physical/scientific target.
- `text_embedding` and `structure_embeddings`: similarity features only.
- `descriptor_text`: generated description, not a target.
- `formula`, `elements_csv`, `space_group`, `crystal_system`, `chemsys`: constraints/facets, not scalar objectives.
- `source`, `source_id`, `retrieved_at`, policy flags: provenance/governance fields.
- `predicted_energy`: candidate-only manifest metadata; not stored per retrieved structure and lacks units/provenance schema.
- `volume` and `nsites`: useful structural descriptors, but should not be presented as material property optimisation targets without a domain-specific reason.

## 6. Missing metadata/provenance gaps

- No general property table exists. Properties are hard-coded columns or JSON fields.
- `band_gap_eV` has a unit in the field name but no value-level source, method, calculation settings, uncertainty, or timestamp.
- Main MCP DB has no populated `band_gap_eV`, so property-conditioned retrieval is blocked for the default workflow.
- Formation energy, energy above hull, dielectric constants, elastic moduli, density, magnetic moment/order, conductivity, and stability labels are absent as stored structure properties.
- MCP schemas do not advertise property inventory, coverage, units, or provenance.
- MCP retrieval results do not include explicit property metadata blocks.
- Candidate manifest metadata has flexible keys, but no schema for units, method, source, uncertainty, or whether a value is predicted vs measured/calculated.
- Fingerprints encode missing numeric values as `0.0`, including missing `band_gap_eV`; downstream users need metadata to avoid misinterpreting missing as true zero.

## 7. Recommended next implementation tickets

1. Add a read-only property registry endpoint/artifact that lists property name, type, unit, source, DB location, coverage, queryability, sortability, and suitability.
2. Add a normalized `structure_properties` table with `structure_id`, `property_name`, `value_num`, `value_text`, `unit`, `source`, `method`, `provenance_json`, and timestamps.
3. Populate `band_gap_eV` for Materials Project ingests from MP summary/property APIs, not CIF-only ingestion; store calculation provenance and unit metadata.
4. Add MCP property filters and sorting, for example `property_filters`, `objective`, `objective_direction`, and `min_coverage_required`.
5. Add property metadata pass-through in `text_search` and `csp_pack` neighbor results, with redaction/policy behavior defined.
6. Add `crystal.property_inventory` or extend `crystal.status` to report property coverage for the selected DB.
7. Add tests for property filter validation, no-invented-property errors, missing-coverage behavior, and MCP result property metadata.
8. Add candidate metadata schema for predicted properties with units, method, source, and prediction/calculation labels.
